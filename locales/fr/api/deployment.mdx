L'**API Apprise** est conçue pour fonctionner comme un service conteneurisé.  
Cette page explique **comment la déployer et l'exploiter**, pas comment utiliser les endpoints de l'API.

Si vous cherchez à :

- envoyer des notifications, consultez **Utilisation de l'API**
- l'intégrer avec la CLI ou la bibliothèque Python, consultez **Intégrations**
- comprendre les clés, le stockage ou le verrouillage, consultez **Configuration**

## Modèle de Déploiement

L'API Apprise est un service **stateless-first** avec un **état persistant optionnel**.

- L'usage stateless envoie les notifications directement sans sauvegarder de configuration.
- L'usage stateful persiste la configuration sous une clé `{KEY}` afin de la réutiliser.
- L'interface web intégrée est optionnelle et fournie uniquement par commodité.

Le service peut être exécuté en toute sécurité :

- localement ;
- derrière un proxy inverse ;
- dans Docker ou Docker Compose ;
- dans Kubernetes, y compris dans des environnements durcis et rootless.

## Démarrage Rapide

Choisissez ci-dessous une méthode de déploiement pour démarrer rapidement l'API Apprise.

<Tabs>
  <TabItem label="Docker">
```bash
docker run --name apprise \
  -p 8000:8000 \
  -v ./config:/config \
  -v ./attach:/attach \
  -e APPRISE_STATEFUL_MODE=simple \
  -e APPRISE_WORKER_COUNT=1 \
  -e APPRISE_ADMIN=y \
  -e APPRISE_DEFAULT_FORMAT=text \
  -d caronc/apprise:latest
```

```bash

  -e APPRISE_ADMIN=y \
  -e APPRISE_DEFAULT_FORMAT=text \

  --health-interval=30s \
  --health-timeout=5s \
  --health-retries=3 \
  --health-start-period=20s \
```


## Stockage Persistant

L'API Apprise prend en charge le stockage persistant pour :

- les configurations enregistrées ;
- les métadonnées d'authentification mises en cache ;
- les pièces jointes téléversées.

Le conteneur attend les chemins inscriptibles suivants :

| Chemin    | Rôle                                        |
| --------- | ------------------------------------------- |
| `/config` | Configurations enregistrées et état interne |
| `/attach` | Pièces jointes téléversées                  |
| `/plugin` | Plugins personnalisés optionnels            |
| `/tmp`    | Fichiers runtime (sockets, buffers, temp)   |

Pour la plupart des déploiements, monter **uniquement `/config` et `/attach`** suffit.

## Déploiements Durcis

Pour des environnements publics ou multi-tenant, l'API Apprise prend en charge une exécution durcie.

Exemple de configuration conteneur durci :

```yaml
services:
  apprise:
    image: caronc/apprise:latest
    container_name: apprise
    user: "1000:1000"
    read_only: true

    cap_drop:
      - ALL

    security_opt:
      - no-new-privileges:true

    ports:
      - "8000:8000"

    environment:
      APPRISE_STATEFUL_MODE: simple
      APPRISE_WORKER_COUNT: 1
      APPRISE_ADMIN: "y"
      APPRISE_DEFAULT_FORMAT: "text"

    volumes:
      - ./config:/config
      - ./attach:/attach

    tmpfs:
      - /tmp
```

Points importants :

- `/tmp` doit rester inscriptible ;
- aucun fichier n'est écrit sous `/var/log` ;
- tous les logs sont écrits vers stdout et stderr.

### Notes de Durcissement pour Kubernetes

Si vous déployez dans Kubernetes, consultez **Démarrage Rapide -> Kubernetes -> Durci (rootless + lecture seule)** pour un exemple prêt à l'emploi qui :

- utilise un système de fichiers racine en lecture seule ;
- monte `/tmp` comme `emptyDir` en mémoire.

## Vérifications d'État

L'API Apprise expose un endpoint de santé :

```text
GET /status
```

- Renvoie HTTP `200` lorsque le service est sain
- Renvoie HTTP `417` si un problème bloquant est détecté

Exemple :

```bash
curl http://localhost:8000/status
```

Cet endpoint convient pour :

- les health checks Docker ;
- les probes de liveness Kubernetes ;
- les systèmes de supervision externes.

## Reverse Proxies et Chemins de Base

Si l'API Apprise est hébergée derrière un proxy inverse ou servie sous un sous-chemin, définissez `APPRISE_BASE_URL` en conséquence.

Exemple :

```bash
APPRISE_BASE_URL=/apprise
```

Cela garantit :

- une génération correcte des URL ;
- un routage correct de l'interface web ;
- des liens OpenAPI corrects.

## Authentification et Contrôle d'Accès

L'API Apprise ne requiert aucune authentification par défaut. Définissez `APPRISE_AUTH_REQUIRED=yes` pour protéger tous les points de terminaison avec HTTP Basic.

| Mode                     | Paramètres                                          | Résultat                                                                                                                                                                      |
| :----------------------- | :-------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Désactivé                | `APPRISE_AUTH_REQUIRED=no`                          | Les requêtes restent ouvertes. Les paramètres d'administration et les connexions de configuration enregistrées sont ignorés.                                                  |
| Administrateur activé    | `APPRISE_AUTH_REQUIRED=yes` avec `APPRISE_PASSWORD` | L'administrateur peut accéder à toutes les clés et gérer les connexions de configuration. `APPRISE_USER` est facultatif.                                                      |
| Administrateur désactivé | `APPRISE_AUTH_REQUIRED=yes` sans `APPRISE_PASSWORD` | Les utilisateurs existants accèdent uniquement à leurs propres clés. Aucune nouvelle connexion ne peut être créée tant qu'un mot de passe administrateur n'est pas configuré. |

`APPRISE_USER` sans `APPRISE_PASSWORD` produit un avertissement au démarrage et laisse le compte administrateur désactivé. Consultez les [Variables d'Environnement](../reference/environment/).

`APPRISE_BASIC_AUTH_REALM` définit le nom affiché dans les invites de connexion. Il ne modifie ni le nom d'utilisateur ni le mot de passe. La valeur par défaut est `Apprise API` ; donnez un nom différent à chaque instance si vous en hébergez plusieurs.

**Utilisez HTTPS/TLS.** Basic ne chiffre pas les identifiants. HTTPS est indispensable en dehors de `localhost` ou d'un réseau de confiance.

Les clients API envoient Basic Auth avec chaque requête. Les requêtes qui acceptent explicitement `text/html` utilisent une connexion signée dans le navigateur. **Déconnexion** peut ainsi fermer l'accès Web sans modifier le fonctionnement JSON ou texte brut de l'API. Les appels API ordinaires ne peuvent pas utiliser ce cookie à la place de Basic Auth.

L'authentification par clé permet de partager un serveur sans partager les identifiants d'administration. Chaque utilisateur reçoit une clé protégée et l'administrateur peut récupérer toute clé.

Dans l'interface Web, ouvrez une configuration, puis sélectionnez son cadenas ou **Authentification** dans le menu. Saisissez un nom d'utilisateur et un mot de passe, puis sélectionnez **Enregistrer**. Les administrateurs globaux peuvent utiliser **Générer Aléatoirement** pour créer les deux valeurs.

L'identifiant de configuration, le nom d'utilisateur et le mot de passe sont trois valeurs distinctes. Utilisez des valeurs aléatoires lorsque cela est possible et transmettez les trois à la personne qui a besoin de l'accès. Le mot de passe enregistré n'est plus affiché par la suite.

Les clients API peuvent protéger une configuration avec `POST /auth/{KEY}`. Un administrateur est requis pour créer la première connexion ou en supprimer une. Les utilisateurs existants s'authentifient avec leur connexion actuelle, répètent le nom d'utilisateur enregistré et fournissent un nouveau mot de passe. Seul un administrateur peut changer le nom d'utilisateur. `APPRISE_CONFIG_LOCK` ne bloque pas ces modifications. Consultez les [Points de Terminaison de l'API](../endpoints/).

Les verrous par clé sont ignorés lorsque `APPRISE_AUTH_REQUIRED` est désactivé, ce qui rétablit le fonctionnement ouvert d'origine. Leurs fichiers sont conservés et redeviennent actifs lorsque l'authentification est activée.

L'interface Web comprend l'option **Déconnexion**, qui ferme immédiatement sa connexion signée. Le navigateur peut conserver Basic Auth en interne, mais ces identifiants en cache ne peuvent pas rétablir silencieusement une connexion HTML.

Les anciens verrous sans configuration sont supprimés après `APPRISE_AUTH_PRUNE_SECONDS` (30 jours par défaut). Les verrous avec configuration sont conservés. Consultez [Élagage](#élagage).

### Vérification de l'Origine du Navigateur

Les navigateurs ajoutent un en-tête `Origin` lorsqu'une page modifie des données. L'API Apprise vérifie cet en-tête et refuse les modifications envoyées depuis un autre site. Les requêtes provenant du même site sont autorisées.

L'API Apprise n'exige pas l'échange de cookie et de jeton CSRF de Django. Les appels directs depuis `curl`, les applications mobiles et les autres programmes restent ainsi simples ; ces clients omettent normalement `Origin` et continuent de fonctionner comme indiqué.

Pour un site HTTPS derrière un proxy inverse, définissez `APPRISE_TRUSTED_ORIGINS` avec l'adresse publique complète, par exemple `https://apprise.example.com`. Séparez plusieurs adresses par des virgules.

Si vous préférez ne pas utiliser ces options intégrées, les approches par proxy inverse restent valables :

- placer l'API derrière un proxy inverse ;
- utiliser une authentification HTTP basic ;
- restreindre l'accès au niveau réseau ou ingress.

Des fichiers de surcharge Nginx peuvent être injectés dans le conteneur pour imposer un contrôle d'accès.

Un exemple Kubernetes utilisant un `Secret` (basic auth `.htpasswd`) et une `ConfigMap` (nginx `location-override.conf`) est disponible dans **Démarrage Rapide -> Kubernetes -> Exemple Complet**.

## Élagage

Le conteneur exécute deux commandes de nettoyage chaque jour. Elles démarrent à 12 heures d'intervalle, utilisent une faible priorité CPU/disque et disposent d'une limite de temps :

| Commande     | Ce qu'elle élague                                                                       | Paramètre de rétention                                         | Paramètre de planification                                                            |
| :----------- | :-------------------------------------------------------------------------------------- | :------------------------------------------------------------- | :------------------------------------------------------------------------------------ |
| `storeprune` | Le stockage persistant d'état de notification propre à Apprise (`APPRISE_STORAGE_DIR`). | `APPRISE_STORAGE_PRUNE_DAYS` (défaut `30` jours)               | `APPRISE_STORAGE_PRUNE_INTERVAL_SECONDS` (défaut `86400`, une fois par jour)          |
| `authprune`  | Verrous Basic par clé sans configuration.                                               | `APPRISE_AUTH_PRUNE_SECONDS` (défaut `2592000`, soit 30 jours) | `APPRISE_AUTH_PRUNE_INTERVAL_SECONDS` (défaut `86400`, démarrage 12 heures plus tard) |

Réglez `APPRISE_PRUNE_ENABLED=no` pour désactiver le nettoyage planifié. `APPRISE_PRUNE_TIMEOUT_SECONDS` modifie la limite de 8 heures. Chaque commande reste exécutable manuellement :

```bash
docker exec -it apprise python manage.py storeprune --days 30
docker exec -it apprise python manage.py authprune --seconds 2592000
```

## Logging et Observabilité

- Tous les logs sont émis vers stdout et stderr
- Aucun fichier log n'est écrit sur disque
- Des métriques Prometheus sont disponibles sur `/metrics`

## Déploiements de Développement

Pour le développement local, le dépôt inclut des surcharges Docker Compose qui :

- montent l'arborescence source locale ;
- rechargent les changements d'UI et de templates sans rebuild ;
- exposent l'API sur le port `8000`.

Ce mode est destiné uniquement au développement et **n'est pas recommandé en production**.

## Étapes Suivantes

Une fois l'application déployée, vous pouvez :

- enregistrer des clés de configuration via l'interface web ou l'API ;
- envoyer des notifications avec `/notify` ou `/notify/{KEY}` ;
- intégrer des systèmes externes via HTTP ou la CLI Apprise.
